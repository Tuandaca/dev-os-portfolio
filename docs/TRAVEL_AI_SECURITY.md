# Travel AI credential exposure — public remediation note

Status: **unresolved; keep the Travel AI repository link off the DEV.OS website.** This is a read-only review of a separate public repository. No credentials were used to authenticate, no live-provider status was checked, and no files or Git history in that repository were changed.

## Findings and limits

| Finding | Assessment | Current evidence |
| --- | --- | --- |
| Neo4j connection credentials | Potential **high** severity until the owner verifies invalidation | The current public tree contains a credential-oriented account note and README material with connection details and two distinct, non-placeholder password-shaped literals. One of those also occurs in a historical environment file. Their syntax and context resemble usable database credentials; validity and database existence are unverified. |
| Google/Gemini API keys | Potential **high** severity until the owner verifies invalidation | Five distinct, non-placeholder Google API-key-shaped values were found across historical revisions of a now-removed environment file. One of those values is also present in two current public notebooks. None was tested. If active, exposure could allow quota or billing abuse. |

The affected material entered the public main-line history across an initial source import in early January 2026, several add/remove cycles of an environment file, a README revision, and a later README copy near the end of January. A targeted review covered the current default-branch tree, 33 current small text/notebook files, five historical environment-file versions, a current compiled Python artifact, and the selected files' commit histories. A byte-pattern scan of that compiled artifact did not find a Google-key-shaped value or Neo4j URI; this does **not** prove the binary is free of secrets. The audit did **not** exhaustively scan the large notebook, every historical blob, forks, caches, deployments, or provider logs. Exact path and commit pointers are intentionally excluded from this public note while potentially active values remain exposed; the owner should obtain the private audit handoff.

## Owner remediation sequence

1. **Treat both database password candidates and all five API-key candidates as compromised.** Identify their owning Neo4j instance(s) and Google project(s) through the provider consoles, not by trying the published values. Rotate or revoke every potentially valid database credential; record provider-side confirmation that old access is invalid. Neo4j documents [instance credentials](https://neo4j.com/docs/aura/getting-started/connect-instance/) and [password changes](https://neo4j.com/docs/operations-manual/current/authentication-authorization/manage-users/).
2. For every Google/Gemini key candidate, create replacements where needed in the owning project, update the application through a private environment or secret manager, then disable or delete the exposed keys. Review API usage, quotas, and billing and apply suitable key restrictions. Follow [Google's leaked-key guidance](https://ai.google.dev/gemini-api/docs/api-key).
3. Remove literal secrets from the **current** public files, notebook inputs and outputs, and examples. Use placeholders in documentation and environment-backed configuration at runtime. Keep real `.env` files and generated bytecode out of Git; review the compiled artifact before removing it in a separately authorized repository change. Add repository secret scanning and review the result. This step does not erase historical copies.
4. Recheck the current tree and provider status without exposing values in logs or tickets. Confirm any running service uses only replacement credentials. Keep the DEV.OS project link withheld until the owner confirms rotation/revocation, current-tree cleanup, and a safe link review.

[GitHub's guidance](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository) puts revocation or rotation before history rewriting. Published Git history, forks, and caches can retain old values; rewriting history is disruptive and requires separate owner approval and collaborator coordination. No history rewrite, force-push, file deletion, or provider action is authorized by this Phase 5A review.
